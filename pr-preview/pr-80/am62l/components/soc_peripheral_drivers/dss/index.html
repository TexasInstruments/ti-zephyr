DSS

Important

The Display Sub-System (DSS) is present on the AM62L SoC family (am62l_evm). Each DSS instance is wired up by the SoC devicetree as exactly one pipeline: one video plane, one overlay, and one video port.

Overview

The TI K3 family Display Sub-System (DSS) is a hardware video composition and output engine. A full DSS instance is built from four kinds of register blocks:

  • VID / VIDL planes — fetch pixel data from a DDR framebuffer via DMA. VID is a full-featured plane; VIDL (“lite”) is a reduced-bandwidth variant.

  • OVR (overlay) — blends one or more plane outputs together and positions them on screen.

  • VP (video port) — generates the pixel clock, HSYNC/VSYNC timing, and drives the physical output bus (parallel DPI or OLDI).

  • Common region — top-level interrupt routing, MFLAG (DMA QoS), and CBA priority configuration shared by all planes/overlays/ports.

The Zephyr driver (tidss, compatible = "ti,tidss") exposes this hardware through the standard display API (<zephyr/drivers/display.h>). A single DT node describes exactly one pipeline:

DDR framebuffer -> one plane (VID or VIDL) -> one overlay (OVR)
                -> one video port (VP) -> DPI pad

The DSS register space is split into four named MMIO regions — "common", "vid", "ovr", "vp". These are logical names: the physical addresses in reg select which actual hardware block (vid, vidl1, vid2 … ovr1, ovr2 … vp1, vp2 …) is used for that region. This lets the same driver bind to any DSS variant — from a single-VP/single-VIDL instance (AM62L) to a multi-VP, multi-plane instance — without driver source changes; only the devicetree node differs.

CONFIG_TI_DSS is selected automatically when an enabled ti,tidss node is present.

Output Routes: DSI vs. DPI/HDMI

The VP’s output pins can be wired to either of two downstream sinks, chosen entirely in devicetree — the tidss driver and the application are unaware of which one is in use:

  • DSI — the VP’s parallel output feeds a MIPI DSI host (Cadence DSI TX on AM62L), which serializes it to a panel such as the ILI9881C. See DSI for the DSI-side driver and devicetree.

  • DPI + HDMI — the VP’s output drives external pins directly as parallel RGB + sync signals, typically into an HDMI bridge chip (e.g. SII9022A).

In both routes zephyr,display stays pointed at &dss itself; the DSI host/panel or the HDMI bridge is a downstream consumer of the DSS output, not a separate zephyr,display target. The ti_sprite sample below demonstrates both routes on the same board via separate devicetree overlays, with no application code changes.

Features Supported

  • display_write() — non-blocking. The call enqueues the supplied buffer into an internal 4-deep request queue and returns immediately.

  • Double buffering: display_get_capabilities() reports SCREEN_INFO_DOUBLE_BUFFER, and display_get_framebuffer() returns a pointer to the buffer that has just finished being scanned out (safe for CPU rendering) rather than the one currently on screen.

  • VSYNC event callback (DISPLAY_EVENT_VSYNC) via display_register_event_callback() / display_unregister_event_callback(). The callback fires from ISR context only, once per confirmed buffer flip — i.e. once the previously submitted frame has actually started being scanned out, not merely queued. Only one callback can be registered at a time.

  • Blanking control: display_blanking_on() / display_blanking_off() disable/re-enable the VP output (VP_CTRL_ENABLE) without tearing down the plane/overlay configuration.

  • Fixed pixel format: PIXEL_FORMAT_ARGB_8888 (4 bytes/pixel). This is the only format reported by display_get_capabilities() and programmed into the VID plane’s DSS_VID_ATTRIBUTES format field.

  • Configurable output bus width (data-width: 12/16/18/24/30/36 bits), covering parallel DPI-style outputs.

  • Configurable sync polarities (hsync-active, vsync-active in the display-timings child node) and panel timings (porches, sync widths, active resolution).

  • SYNC_LOST detection: the ISR logs an error and returns early on a VP_IRQ_SYNC_LOST interrupt (DSS pipeline underrun/stall), without touching buffer state.

Features NOT Supported

  • Pixel formats other than ARGB8888 — no RGB565, YUV, or indexed-color path is implemented.

  • Multiple simultaneous planes/overlays per DSS instance — the driver manages exactly one VID/VIDL plane feeding exactly one overlay layer (layer 0) and one video port. Multi-plane composition (e.g. a second overlay layer) is not exposed.

  • Premultiplied alpha and per-plane global alpha blending — global alpha is fixed at 0xFF (opaque); display_set_contrast() / brightness-style APIs are not implemented.

  • Display rotation/orientation — display_get_capabilities() always reports DISPLAY_ORIENTATION_NORMAL; no rotation path exists.

  • Runtime pixel format negotiation (display_set_pixel_format()) — not implemented; the format is fixed at build/init time.

  • Polling/non-ISR delivery of the VSYNC callback (display_register_event_callback() with in_isr = false) returns -ENOTSUP.

Enabling the Driver

The dss node is defined (but disabled) in the AM62L SoC devicetree. Set the panel/output parameters and route zephyr,display to it in the board or application overlay:

&dss {
        data-width = <24>;
        height = <1280>;
        width = <720>;

        display-timings {
                compatible = "zephyr,panel-timing";
                clock-frequency = <83330000>;
                hfront-porch = <239>;
                hback-porch = <50>;
                hsync-len = <33>;
                vfront-porch = <20>;
                vback-porch = <30>;
                vsync-len = <2>;
                hsync-active = <0>;
                vsync-active = <0>;
                de-active = <1>;
                pixelclk-active = <0>;
        };

        status = "okay";
};

/ {
        chosen {
                zephyr,display = &dss;
        };
};

CONFIG_DISPLAY=y

Important

zephyr,display should point at the DSS node itself, even when the physical output passes through a downstream bridge or panel (DSI host, HDMI bridge, etc.). Those downstream devices are configured and brought up independently — they consume the DSS’s DPI output signal, they are not separate zephyr,display targets. The application always renders ARGB8888 frames into the buffer handed to tidss.

Devicetree Properties

DSS node (compatible = "ti,tidss")

Property

Description

reg / reg-names

Four MMIO regions, in order "common", "vid", "ovr", "vp". The physical addresses select which hardware plane, overlay, and video port this pipeline instance uses.

ti,vp-index

0-based index of the video port used by this pipeline (0 = VP1, 1 = VP2, …). Used for per-VP IRQ enable/status register offsets.

ti,vid-channel

CHANNELIN value written into the overlay’s attribute register:

data-width

Output bus width in bits: 12, 16, 18, 24, 30, or 36. Encoded into the video port’s data-line-count field.

width / height

Active resolution in pixels (inherited from the generic display-controller.yaml binding).

clocks / clock-names

Two clock entries named "vp" (video port pixel clock) and "fclk" (functional clock). The pixel clock rate is set from clock-frequency in the display-timings child node.

pinctrl-0, pinctrl-names

Pin control state(s) for the DPI output pins actually in use (varies by route — e.g. a DSI host needs no DSS pin muxing, while a parallel DPI route requires the full dss_vout0_* pin group).

display-timings child node (compatible = "zephyr,panel-timing")

Property

Description

clock-frequency

Pixel clock in Hz.

hfront-porch / hback-porch / hsync-len

Horizontal front porch, back porch, and sync pulse width, in pixel clocks.

vfront-porch / vback-porch / vsync-len

Vertical front porch, back porch, and sync pulse width, in lines.

hsync-active / vsync-active

Sync pulse polarity: 1 = active-high, 0 = active-low. The driver inverts internally where the hardware expects the opposite sense.

de-active / pixelclk-active

Data-enable and pixel-clock edge polarity. Accepted by the binding; passed through for consistency with the panel-timing schema used elsewhere in Zephyr.

Usage

Non-Blocking Write with VSYNC Callback

#include <zephyr/device.h>
#include <zephyr/drivers/display.h>
#include <zephyr/kernel.h>

static K_SEM_DEFINE(frame_done, 0, 1);

static void vsync_cb(const struct device *dev, enum display_event_type type,
                      struct display_event_data *data, void *user_data)
{
        ARG_UNUSED(dev);
        ARG_UNUSED(type);
        ARG_UNUSED(data);
        ARG_UNUSED(user_data);

        k_sem_give(&frame_done);
}

void render_loop(const struct device *disp)
{
        struct display_capabilities caps;
        uint32_t reg_handle;

        display_get_capabilities(disp, &caps);

        display_register_event_callback(disp, vsync_cb, NULL,
                                         DISPLAY_EVENT_VSYNC,
                                         true /* in_isr */, &reg_handle);

        struct display_buffer_descriptor desc = {
                .width  = caps.x_resolution,
                .height = caps.y_resolution,
                .pitch  = caps.x_resolution,
                .buf_size = caps.x_resolution * caps.y_resolution * 4,
        };

        while (1) {
                /* fb points at a double-buffered ARGB8888 frame
                 * rendered by the application */
                display_write(disp, 0, 0, &desc, fb);

                /* Wait for the driver to confirm the flip at VSYNC */
                k_sem_take(&frame_done, K_FOREVER);
        }
}

Blanking

display_blanking_on(disp);   /* VP output disabled, writes dropped   */
display_blanking_off(disp);  /* VP output re-enabled                 */

Note

display_write() out-of-bounds (x + width or y + height exceeding the configured width/height) returns -EINVAL and logs an error; it does not clip or partially render the buffer.

Samples

ti-zephyr

  • TI DSS Sprite Animation — slides a sprite across the display in a serpentine pattern using the fully non-blocking, VSYNC-callback-driven path described above. Runs on am62l_evm/am62l3/a53 with two selectable output routes:

    • DSI + Raspberry Pi Touch Display 2 (default overlay) — 720x1280 over 2-lane MIPI DSI via a Cadence DSI TX bridge; matches the board’s default DSS timings.

    • DPI + HDMI (boards/am62l_evm_am62l3_a53_hdmi.overlay, selected with -DDTC_OVERLAY_FILE=...) — 1920x1080@60 Hz over 24-bit parallel DPI to an SII9022A HDMI bridge, overriding the default panel timings and pin muxing.

    In both routes zephyr,display stays pointed at &dss; the DSI/HDMI hardware is a downstream sink for the DSS output, not a separate zephyr,display target.
